# Static-bake coverage report (offline planner probe)

Generated by `StaticBakePlanProbe` over 12 recording(s). Each scene is forced fully
stable, then run through the REAL `StaticBakePlanner` with the additive sub-quad + per-region
levers active. `effectStaticOk` is swept two ways to bound the shader contribution:
`EMPTY` = no shader cleared (every shader ends its prefix); `ALL` = every shader cleared (the
maximum the controller could ever allow, on-device gated by mount / blend-class / screen-read).

Numbers are the PLAN (not a rendered frame): `mix`/`add` = baked nodes per partition, `live` =
re-leveled live band painters, `elig` = per-node eligible painters in the paint order.

> OFFLINE CAVEAT: bottomOnly / addBlend come from `CanvasBlendMode` only (no Godot ShaderStore),
> so an additive-blend SHADER would read Mix here. Combat's water shader IS Mix and its additive
> content is atmosphere PARTICLES (hard-rejected), so combat coverage is faithful.

`bucketZ` = the bottom bucket effZ (a real background band is < 0; 0 = flat/spine background).
`addBand` = additive (CanvasBlendMode Add) painters IN the bottom bucket / total — where the add
sub-quad could help. `bnd` = the node type that ended the baked band.

## Findings

- **9/12** scenes bake under the `ALL` sweep; **0/12** under `EMPTY` —
  EVERY bakeable scene needs its background shader cleared first (the boundary under `EMPTY` is the
  water/room `shader`). On-device that clearance is gated by Static-clone fidelity (WS-EMITTER's
  `MaterialSamplerStore`, Part 1) — until that lands, combat baking is not AE-safe on device.
- **7/12** scenes have a real z<0 background band. The combat/room band bakes a
  NON-TRIVIAL 3–5 regions / 22–38 mix nodes once the shader is cleared (the ~33% background-fill
  prize). The band always ends at an atmosphere `particle` (`floorfog`) — v3 multi-region jumps it.
- **3 scenes have a SPINE background** (bucketZ 0, boundary `spine`): two combat recordings
  (…37-42, …38-48) and audit-shop. A spine-drawn backdrop is dynamic pixels — legitimately
  unbakeable. This is the per-encounter content variance the planner must stay generic about: NOT
  every combat has a z<0 static band.
- **Additive sub-quad (Part 2): 0 add partitions OFFLINE** (this probe classifies Add by
  CanvasBlendMode only; the 139 in-band plain-Add painters here all sit in region 0 or a
  particle gap). LIVE it is different + WORSE: the Godot ShaderStore flags ~65 combat background
  layers as Add-blend SHADERS, so the real combat band is heavily additive-interleaved.

## Live-render reality (device/Xvfb, NOT visible to this offline probe)

- **restsite / rewards / event / cardreward bake CORRECTLY** (mix regions), ON-vs-OFF `AE=0` (fuzz-2%,
  Full) — the water/room shaders in those bands clone faithfully (blocker #1 is a NON-issue: the
  water `noise` is a `.tscn` NoiseTexture2D kept at the shader default for BOTH live and clone, so it
  is identical). MaterialSamplerStore (`.tres` Curve/Gradient) never touches a baked node.
- **Combat does NOT get a correct fill bake.** Its z=-10 band is ~65-way additive-interleaved LIVE:
  with the add sub-quad OFF (default) those additive shaders stay live and fragment the mix runs
  below `MinPaintersPerRegion` → the band does not bake (SAFE, no artifact, no fill win). With the
  add sub-quad ON the band DOES bake (3 regions / ~19 nodes) but the additive-over-re-leveled-live
  composite is wrong: `AE≈107k` vs a ~14k particle jitter floor → the add sub-quad is DEFAULT OFF
  (opt-in `…_ADDQUAD=1`). Correct combat baking needs a per-depth additive composite, not one add
  quad per region — the remaining real blocker.

## WS-BGBAKE band-flatten mode (Jul 28-29 2026 — combat finally bakes)

The exact planners above never held a bake in LIVE combat (0 regions; the ~65-way additive-
interleaved z<0 band + per-drain churn). `PlanBandFlatten` (bgBake setting, default ON inside the
bake opt-in; combat + bucketZ<0 only, everything else takes the exact path byte-identically) trades
exact mid-band ordering for fill: quad A = every eligible static below the LAST live interloper,
quad B = the ordering-exact trailing Foreground run, ~40 interlopers re-leveled live between.
Live combat: 2 regions / ~106-118 nodes / ~10.6 design-screens of fill collapsed to 2.

Why it HOLDS (each fix measured on the looping canonical replay before/after):
1. OrderChanged band-prefix guard (`bakeOrderSkips`) — combat reorders z≥0 ~7/s; keep the bake
   when the z<0 prefix is element-identical.
2. Room-scoped 2-strike bench — the ~9s wave banner (NinePatch Draw + MegaLabel Text) exiles to a
   live interloper for the room; room boundary = DEBOUNCED screen-type change (20 drains), NOT
   keyframe (resyncs/loops must not un-teach it).
3. Carrier transform follow (`bakeCarrierFollows`) — screen shake = Transform-only change on the
   band-root NCombatSceneContainer (a spine carrier: ancestor of ALL baked members); quads are
   retransformed by current×bakedInverse instead of torn down.
4. Subtree bench — a FADING non-spine carrier (the enemy Intents HBoxContainer, modulate hints per
   enemy action) exiles its whole subtree (safe: never an ancestor-of-all, blast radius = itself).

Result (moto g86, Full renderScale): Active windows 47 fps / p50 20.4ms / p95 26-28 vs 35.6 /
27.3 / 32.7 with bgBake off; spike frames halved. Gap to the 56.8 hide-bg ceiling = the live
interlopers the plan correctly refuses: the 5 full-screen Sub/Mul light/shade layers (the next
fill prize), fog particles, uncleared shaders. Diagnostics: `M3_BAKE_PLAN` (`band=`),
`M3_BAKE_INVALIDATE` (culprits + change flags), `M3_BAKE_DECISION` (policy branch), QA state
`bakeBand/bakeLiveZ/bakeOrderSkips/bakeCarrierFollows`.

## How to verify WS-BGBAKE (round 3)

The band-flatten bake has exactly two user-facing requirements, and one enforcing artifact each. The two live
gates run on desktop (Xvfb + a live asset origin on `:13337`; they do NOT launch the game). The two pure suites
ride the normal `dotnet run --project tests/CouchCoop.MirrorProtocol.Tests` (the custom Exe runner — NOT `dotnet
test`).

### Requirement 1 — "the optimized bg is applied EVERY frame of the loop"

* **`scripts/verify-bgbake-residency.sh`** (~3 min). Own Xvfb (display ≥ `:60`) + own `replay-ws-server.mjs`
  (`--loop`, recorded pace, proxying assets from `:13337`) + the native client in `--connect` mode with a single QA
  connection, at **2401x1080** with **shaders Static** (`COUCHCOOP_EFFECTS=static` — the shipping device config AND
  the only mode the band plan has anything bakeable under; particles stay dynamic as realistic live interlopers). It
  arms the bake, warms up one loop, then samples `state` across ~4 loop seams and asserts:
  - **(a) `bakeUnbakedVisibleFrames` delta == 0** — THE frame-accurate every-frame guarantee: not one frame of raw
    (un-baked) scene after a room has baked. This is the whole requirement.
  - **(b) `bakeStaleDrops` delta == 0** — no stale double-buffer picture was ever hard-dropped visible.
  - **(c) `bakeGenSwaps` delta ≥ 2** — ≥2 loop seams were absorbed by the INVISIBLE atomic-rebake path (stale quads
    stay shown while the replacement builds; `SwapGeneration` swaps in one `_Process` frame).
  - **(d)/(e)** every sample `bakeState ∈ {Active,Rebaking}` (Idle/Baking recovery windows tolerated iff (a) holds),
    `bakeRegions ∈ {0,3,6}`, `bakeLiveZ ∈ {0,42}` — the canonical combat plan is 3 regions / 42 live-z; `6` is the
    transient double-buffer (old + new generation), `0` only during an Idle recovery window.
  - **(f)** a DISTINCT failure if the `bakeUnbakedVisibleFrames` key is missing from the state JSON (contract
    regression). Pass line: `BGBAKE_RESIDENCY: ALL PASS`.
* **`BandResidencyReplayProbe.cs`** (pure, env-gated on the canonical recording; silent-skips in a clean checkout).
  Replays the recording delta-by-delta through the SAME pure classes the controller drives —
  `StaticBakePlanner.ObserveDrain/ObserveFrame` + `BandResidencyMachine.EvaluateStructure/EvaluateCulprits` — and
  asserts the same residency property offline: on this recording the pure model arms once (drain 10) and holds the
  bake teardown-free for all 1179 subsequent drains (181 OrderChanged absorbed as ProceedOrderSkipped, 135 screen-
  shakes as carrier Follows, 945 ordering-exact plans), so the measured learning window is 0 (pinned at 8 with
  headroom). The loop-seam keyframe (identical re-send) SURVIVES (never a KeyframeDrop) with an unchanged plan
  signature and zero re-learning.

> **Loop-seam reality (AMENDS the plan file, which predates the retain-rebake design).** Live loop seams are NOT
> clean "survives": the looping replay re-sends its frame-0 snapshot while the active state is the recording's final
> frame, so the band prefix content differs → the seam is a **KeyframeRetain** (invisible rebake behind the stale
> quads; `bakeGenSwaps++`, `bakeKeyframeSurvives` stays 0). A minority of seams (drain-timing dependent) rewind a
> **structurally different** scene (a creature mid-death/respawn, ~656→547 nodes) → a deliberate **DROP** class →
> `bakeState` goes Idle for a short recovery window and the RAW scene shows briefly. That is design-correct (a real
> scene change must show raw), and the `bakeUnbakedVisibleFrames` gate **excludes** it (its residency window re-opens
> on DROP). This is why the residency gate asserts (a) delta 0 + (c) gen-swaps ≥ 2, and does **not** assert
> "rebakes/builds delta 0".

### Requirement 2 — "the optimized bg looks EXACTLY the same as the unoptimized one"

* **`scripts/verify-bgbake-parity.sh`** (~10-12 min). Deterministic env `COUCHCOOP_EFFECTS=static` +
  `COUCHCOOP_MIRROR_SPINE_FREEZE=1` (a TRUE OFF-vs-OFF `AE=0` floor). Per resolution ∈ {**1920x1080, 2401x1080**},
  three single-drain `--replay --shot` legs (off-a / off-b / on) gated by:
  - **non-vacuity** — each shot is non-blank (image std-dev), and the ON log's settled `M3_BAKE_PLAN:
    bakeable=True band=True regions≥1` proves the band bake actually engaged (else "AE=0" is trivially true);
  - **determinism** — `AE(off-a, off-b) == 0` (the parity floor precondition);
  - **structural** — `AE -fuzz 20%` (on vs off) `== 0`: nothing moved past a 20% tolerance — no floating tree, no
    ember bleed-through, no re-leveled layer. The band composites in the exact same PLACE;
  - **brightness** — `AE -fuzz 2%` (on vs off) `≤ BGBAKE_AE_BUDGET`: the only residual;
  - **HP crops** — `AE == 0` EXACT on the ally + enemy health-bar crops. The excluded-live-subtree design means the
    HealthBar is NEVER baked, so it is byte-identical — this is the round-2 stale-orange-bar regression's direct
    gate. Crop non-vacuity is asserted on the OFF crop so the geometry provably contains the bar.
  Plus a **connect-mode staleness leg** at 2401x1080 (`--shot-after 26`, no loop): a single `--replay` drain bakes on
  the FINAL state and can never catch HP staleness, so this leg streams the HP values changing live over 26s and
  proves the excluded HP subtree still matches OFF (fuzz-tolerant — connect mode has weaker determinism than the
  single-drain `--replay`). Pass line: `BGBAKE_PARITY: ALL PASS`.
* **`BandOrderingExactTests.cs`** (pure, always-on). The structural proof behind requirement 2: for every synthetic
  band plan, expand its slots — quads → baked painters, live overrides → their painter, excluded roots → subtree
  painters — sort by absolute z, and `SequenceEqual` the raw band's painting-node sequence in paint order. Any
  hoist, drop, duplicate, or occlusion inversion (the entire round-2 defect class) fails. Cases: segmented split
  (`s8|P0|m6|P1|t4 → 3` regions), no-hoist-across-interloper, tiny-run-stays-live, excluded-root subtree, Sub/Mul
  demotion, keyframe-seam signature equality (+ changed-band negative), guard tolerance under excluded-subtree churn.
  The same `BandOrderingExact.AssertOrderingExact` checker runs on every plan the residency probe produces.

### The documented Sub/Mul brightness residual + budget rationale

The structural gate (`-fuzz 20%`) proves nothing moved; the brightness gate (`-fuzz 2%`) is where the ONLY
difference lives, and it is irreducible. A Sub/Mul-blend band member is baked into its region quad and composited
back as a premultiplied "over" quad; the 8-bit round-trip of that composite rounds to RGBA8 a hair differently from
the live raw Sub/Mul draw. It is **structurally invisible** (below a 2% per-channel tolerance almost everywhere,
never a moved edge). Measured on the canonical recording: `AE -fuzz 2%` = **155459 @2401** / **89302 @1920**.
Budgets are pinned WITH headroom: `BGBAKE_AE_BUDGET_2401=200000`, `BGBAKE_AE_BUDGET_1920=120000` (both env-
overridable). The wider budget at 2401 is expected — more baked band pixels at the wider design width means more
8-bit round-trips. Archived side-by-side + diff evidence: `diff-bright-<res>.png` in the script's OUT dir.
